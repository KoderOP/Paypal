# FINORA — Know the impact before money moves.

**An AI-powered financial decision copilot that forecasts the impact of a purchase, compares payment strategies, and prepares a
PayPal checkout with human authorization at every critical step.**

FINORA turns transaction history into a day-by-day forecast of your balance. Ask *"Should I buy a ₹75,000 laptop?"* and it
shows what each way of paying does to your future cash flow. If you decide to go ahead, it prepares a PayPal checkout that only
you can authorise.

> [!IMPORTANT]
> **The demo uses fictional data.** The sample profile contains about 300 synthetic transactions generated by FINORA in
> PayPal's Activity-report format. The exact count depends on the date; the landing page shows it. None of it is real customer
> data or came from PayPal. A *Sample data* strip stays on every page while it's loaded, and every transaction records its source.

## The ₹75,000 laptop, step by step

Figures from a run on 12 Nov 2026 with the sample profile and the default ₹20,000 safety buffer. The sample is generated
relative to today, so exact amounts shift slightly by date. The conclusions don't: a test checks them on dates across a full year.

1. **You ask:** *"Should I buy a ₹75,000 laptop?"*
2. **The engine calculates.** It projects the balance day by day, with and without the purchase, for each way of paying:

   | Option | Lowest projected balance | Safety buffer |
   |---|---|---|
   | Pay in full today | ₹13,260 (23 Nov 2026) | **Below for 7 days** before the next salary |
   | Wait until payday (24 Nov) | ₹33,252 | Stays above |
   | Pay in 4 (₹18,750 today, then 3 × ₹18,750) | ₹52,002 | Stays above, no extra cost |
   | Pay Monthly, 12 months | ₹1,01,305 | Stays above, ₹8,367 extra at 19.99% APR |

3. **Why paying in full is risky:** rent, bills and day-to-day spending fall before the next salary, so the balance would sit
   under the buffer for a week.
4. **What it recommends:** *Pay in 4.* It's the cheapest option that keeps you above your buffer and gets you the laptop today.
5. **What FINORA does with PayPal:** on *"Go ahead with Pay in 4"* it prepares a checkout **proposal**. You acknowledge it.
   FINORA then creates a PayPal **Orders v2** order, you **approve it on PayPal**, and you **confirm the capture** in FINORA.
   Only then is money captured. The twin then records the payment.
6. **What is illustrative:** Pay in 4 and Pay Monthly terms (APR, schedule, eligibility) are FINORA's illustrative inputs for
   comparing options. PayPal decides real Pay Later eligibility and terms on its own approval page.

## Judge's Quick Start

**The fastest path is to run it locally (about 2 minutes, no keys needed).** The Codespaces preview link used during
development (`https://stunning-doodle-x595pv6x7xpqh9wq-5173.app.github.dev/welcome`) redirects to a GitHub sign-in: it's a
private port of a development environment, not a public deployment.

```bash
git clone https://github.com/KoderOP/Paypal && cd Paypal
cd backend && python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
uvicorn app.main:app --port 8000          # terminal 1
cd frontend && npm install && npm run dev  # terminal 2, from the repo root
```

Then:
1. **Open <http://localhost:5173>.** The landing page shows the engine's payment-impact preview for the sample profile.
2. Click **Launch the live demo**. This loads the fictional profile and asks the agent about the ₹75,000 laptop.
3. Read the answer: verdict, payment strategies and chart. Expand **Technical details** to see the tool call and grounding check.
4. Open **What-if Simulator** for the forecast, the optimal purchase window, the payment matrix and the Cash-Flow Risk Analysis.
5. Back in **Ask FINORA**, click **Go ahead with PayPal Pay in 4** (or *Pay in full now with PayPal*) to get a checkout proposal.
6. Tick the acknowledgement and click **Continue to PayPal**. Without credentials this opens FINORA's labelled **PayPal demo
   mode**; with [Sandbox credentials](#paypal-sandbox) it opens real `sandbox.paypal.com`. Approve, then **Confirm and pay**.
7. Open **PayPal Hub** (*What's connected, and what's real*) and **Evaluation** for the technical evidence.

Without a Groq key, an offline planner answers common questions exactly (marked *Offline mode*). With `GROQ_API_KEY`, the AI
assistant handles free-form questions.

## Why FINORA is different

- **It works before the money leaves.** Most finance apps report what you already spent. FINORA answers the question at the
  moment of decision and connects the answer to PayPal checkout.
- **The engine calculates; the AI doesn't.** Balances, forecasts and comparisons come from a deterministic, tested engine
  (Decimal money, same inputs → same outputs). The language model picks which calculation to run and explains the result.
- **Financial claims are checked.** A guardrail validates every amount, percentage and date in an AI answer against the
  engine's output. Failing drafts are replaced with the engine's own wording, and the answer says so.
- **You stay in control of payments.** The agent can only prepare a proposal. Three human steps, each enforced on the server,
  stand between that proposal and a captured payment.
- **Evidence over claims.** Four reproducible evaluations with baselines and stated limits, visible in-app at `/evals`.

## Why FINORA is an agent

```
User intent
 → intent interpretation            (Groq LLM, or the offline planner)
 → financial tool selection         (one or more of 7 engine tools, with arguments)
 → deterministic financial computation
 → numerical grounding validation   (money, percentages, dates vs tool results)
 → recommendation
 → checkout proposal                (prepare_paypal_checkout: proposal only)
 → human acknowledgement            (server rejects without it: 422)
 → PayPal approval                  (buyer approves on PayPal)
 → explicit capture confirmation    (server rejects without confirm=true: 422)
```

- **The LLM selects from seven tools:** `get_financial_snapshot`, `compare_payment_options`, `find_affordability`,
  `simulate_scenario`, `run_stress_test`, `get_cross_border_summary`, `prepare_paypal_checkout`. It can call several in one
  turn (up to 4 rounds) and build on the previous answer ("and what if my salary is also late?").
- **`prepare_paypal_checkout` returns a proposal and creates nothing.** No tool can create an order or capture a payment. The AI
  cannot bypass the confirmation steps, because they're checks in the checkout API, not instructions to the model.
- **If the provider fails** (rate limit, outage, malformed tool call), the client retries, switches to a fallback model, or hands
  the question to the deterministic planner. The answer is labelled accordingly.

## PayPal integration matrix

| Capability | FINORA implementation | Verification status |
|---|---|---|
| OAuth 2.0 (client credentials) | `integrations/paypal/client.py`; live *Test connection* in PayPal Hub | **Live-verified** (Sandbox) |
| Orders v2: create order | `POST /api/checkout/orders` (needs `acknowledged: true`); idempotency key | **Live-verified** (Sandbox) |
| Buyer approval on PayPal | Redirect to PayPal, return to `/api/checkout/return` (status re-checked with PayPal) | **Live-verified** with a US Sandbox buyer |
| Capture with explicit confirmation | `POST /api/checkout/orders/{id}/capture` (needs `confirm: true`); PayPal returned `COMPLETED` | **Live-verified** (Sandbox, USD 892.86) |
| Transaction Search sync (read-only) | `POST /api/integrations/paypal/sync`; currency conversion; provenance `paypal_api` | **Live-verified** (Sandbox record synced) |
| Subscriptions API (link, refresh, cancel, suspend, activate) | `api/subscriptions.py`; each action needs `confirm: true` | Implemented; **mocked tests and demo mode only** |
| Log in with PayPal (OpenID Connect) | `api/auth.py`, `integrations/paypal/identity.py`; optional | Implemented; **mocked tests and demo mode only** |
| Pay in 4 / Pay Monthly | Engine schedules from **illustrative** terms; the Orders v2 checkout itself is real | **Illustrative**: no PayPal financing API; PayPal decides eligibility and terms |

**Sandbox currency.** The tested Sandbox flow doesn't accept INR (`422 Currency code is not currently supported`). FINORA charges
USD when `PAYPAL_CHECKOUT_CURRENCY=USD`, converting at **your** `PAYPAL_CHECKOUT_FX_RATE` (example: 84 INR per USD, so ₹75,000 →
USD 892.86). The rate is user-configured, not fetched from PayPal. Approval needs a **US-registered** Sandbox buyer account.
India-registered buyer accounts were refused.

**PayPal demo mode.** With no credentials, an in-process stand-in for these endpoints runs the same client code. Every page
labels it as demo mode; nothing is sent to PayPal and no money moves.

## Architecture

```
 PayPal Transaction Search / Activity CSV / bank CSV / sample profile
            │ 1. ingestion + provenance (origin: sample | user_import | paypal_api | paypal_checkout)
            ▼
 ┌──────────── 2. deterministic engine (pure, Decimal-only, no I/O, no LLM) ──────────┐
 │ twin.py  recurring detection · variable spend │ forecast.py  90-day daily path      │
 │ payment_options.py  now / wait / Pay Later    │ goals.py  max safe spend, safe date │
 │ scenarios.py  composable what-ifs             │ stress.py  shocks + Monte Carlo     │
 └───────────────────────────────▲────────────────────────────────────────────────────┘
                                 │ 7 tools (JSON schema)
 ┌──────────── 3. agent (app/ai) ┴────────────────────────────────────────────────────┐
 │ Groq chat completions + tool calling ⇄ tools; fallback: deterministic planner      │
 │ 4. guardrail: every ₹ amount, % and date in the draft must come from tool results  │
 └───────────────────────────────┬────────────────────────────────────────────────────┘
                                 │ prepare_paypal_checkout = proposal only
                                 ▼
  5. human-controlled checkout: acknowledge → PayPal Orders v2 approval → confirm capture → twin updated
```

How the tools work together: `get_financial_snapshot` describes where you stand. `compare_payment_options` and
`find_affordability` answer purchase questions. `simulate_scenario` composes what-ifs. `run_stress_test` and
`get_cross_border_summary` cover resilience and foreign income. `prepare_paypal_checkout` turns a chosen option into a proposal
for the human-controlled checkout.

## Evaluation results

All four evaluations are reproducible (`cd backend && python -m evals.run_all`; add `--llm` with `GROQ_API_KEY`). **None of them
measures real-customer accuracy:** they use synthetic histories and the fictional sample profile.

| Evaluation | Headline | Comparison |
|---|---|---|
| Live Groq agent (`openai/gpt-oss-120b`), 40 questions | Tool **92.5%**, arguments **90%**, grounded **100%** | Held-out paraphrases: 78.6% tool / 71.4% arguments |
| Offline planner, same 40 questions | Tool 85%, arguments 77.5%, grounded 100% | Held-out paraphrases: 57.1% / 35.7% |
| Forecast backtest, synthetic, noise-injected | Purchase-safety decisions **95.0%**, false-safe 3.5% | Seasonal naive 92.6% / 4.6% |
| Guardrail red-team | **97.7%** of 262 corrupted drafts caught, 0% of 154 faithful drafts rejected | Flat 1% tolerance: 76.3% caught |

<details>
<summary><b>Methodology and limitations</b></summary>

**Live Groq benchmark.** 40 questions (26 in wording the offline planner was written for, 14 held-out paraphrases), including
multi-turn follow-ups and checkout requests, paced to Groq's free-tier 8,000 tokens/minute. **15%** of answers fell back to the
offline planner after temporary provider errors (those answers were still grounded). **17.5%** of drafts were rewritten by the
guardrail; across three full runs that rate was 20%, 7.5% and 17.5%. In the rewrites we reproduced, the model had done its own
arithmetic (once incorrectly). Small sample: 40 questions.

**Forecast backtest.** 30 seeds × 2 personas = 60 synthetic six-month histories, 5 walk-forward cut-offs each (300 forecasts per
model), 30-day horizon. Baselines: flat balance, linear drift, seasonal naive. On clean synthetic histories: 96.8% vs 93.2%.
Daily balance error, noise-injected: 15.6% of monthly income vs 20.0%. The generator has the monthly structure the twin looks for,
which favours it. Run `python -m evals.forecast_backtest --file <your export.csv>` on real data.

**Guardrail red-team.** Faithful rewrites (lakh/K notation, rounding, long dates) must pass; corruptions (×1.005, ×1.05, ×1.2, ×0.5,
digit swaps, fabricated sentences, shifted dates and percentages) must be caught. The 2.3% misses are coincidences with other
legitimate figures, a limit of value-based grounding.

Full tables: [docs/EVALUATION.md](docs/EVALUATION.md) and the in-app Evaluation page.
</details>

## Data provenance

Every account records **where its data came from** when it's stored; it's never inferred from file format.

| Origin | What it is | Label in the app |
|---|---|---|
| `sample` | FINORA's fictional profile (or an uploaded `finora-demo-*` / `SAMPLE…`-id file) | *Sample · fictional* + the Sample data strip |
| `user_import` | A file you uploaded | *Your imported file* |
| `paypal_api` | Records from PayPal Transaction Search, with environment | *PayPal Sandbox · Transaction Search* |
| `paypal_checkout` | Payments captured through FINORA's checkout, with environment | *PayPal Sandbox · Orders API capture* |

- **Fictional and real data never share a ledger.** Adding real data while the sample is loaded is refused (409) unless you replace
  it, and vice versa. Checkout captures are the demo payment itself, recorded in their own labelled account.
- **The PayPal Hub counts only `paypal_api` and `paypal_checkout` as PayPal records.** It shows the checkout states
  (`awaiting_approval` → `approved` → `captured`, or `failed` / `cancelled`) with real PayPal order and capture IDs.
- **Reconciliation:** balance = Σ opening balances + Σ transactions. Dashboard, agent and simulator share one snapshot and one
  reference date (tested).
- **Currencies:** Transaction Search records in another currency are converted only at your configured rate (original amount, fee
  and rate kept) or skipped and reported. Deposits, withdrawals, transfers and opening funding are transfers, not income.
- PayPal transaction IDs are stored once per user, so an Activity export plus an API sync don't double count.

## Installation and configuration

**Requirements:** Python 3.12+ (the Docker image uses 3.12; also run on 3.14) and Node.js 20.19+ or 22.12+ (Vite's
requirement; the Docker image uses 22).

```bash
# Backend: http://localhost:8000 (OpenAPI docs at /docs)
cd backend && python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

# Frontend: http://localhost:5173 (second terminal)
cd frontend && npm install && npm run dev
```

**Configuration:** copy `.env.example` to `.env` (repo root, or `backend/.env`). With no `.env`, everything runs offline: the
offline planner answers, PayPal runs in labelled demo mode, and SQLite is used.

| Setting | Purpose |
|---|---|
| `GROQ_API_KEY`, `GROQ_MODEL` (`openai/gpt-oss-120b`), `GROQ_FALLBACK_MODEL` (`openai/gpt-oss-20b`) | AI assistant. Check with `cd backend && python -m evals.check_groq` |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_BASE_URL` | PayPal Sandbox (defaults to the Sandbox URL) |
| `PAYPAL_CHECKOUT_CURRENCY=USD`, `PAYPAL_CHECKOUT_FX_RATE=84` | Charge USD in Sandbox, converted at your rate |
| `CHAT_RATE_LIMIT_PER_MINUTE` | Protects the Groq quota (default 20 per client) |

### PayPal Sandbox

1. developer.paypal.com → Apps & Credentials → **Sandbox** app → copy the client ID and secret into `.env`. Under the app's
   Features, enable **Transaction search** for sync.
2. Set `PAYPAL_CHECKOUT_CURRENCY=USD` and `PAYPAL_CHECKOUT_FX_RATE` (INR per USD, your choice).
3. Create a **US-registered** Sandbox *Personal* buyer account (Testing Tools → Sandbox Accounts). Use a private window if the
   browser remembers another Sandbox login.
4. `cd backend && python -m evals.check_paypal` runs a real Sandbox OAuth, a $1 order and (`--capture ID`) a capture, using the
   app's own client code.

**Docker:** `docker compose up --build` starts PostgreSQL 16, the backend and the frontend.

## Honest limitations

- **Fictional data everywhere in the demo and evaluations.** The sample profile is synthetic; the forecast backtest uses synthetic
  histories. No figure here is real-customer accuracy.
- **Pay Later is illustrative.** Pay in 4 / Pay Monthly terms are FINORA's inputs; PayPal decides eligibility, APR and schedule at
  checkout. After a capture, the instalments FINORA records (including the first) are a simulated schedule.
- **Not verified live:** Subscriptions API actions, Log in with PayPal, and a Pay Later approval on PayPal. These are covered only
  by mocked HTTP tests and demo mode.
- **Currency conversion uses your configured rate**, not PayPal's or a market rate.
- **Groq free tier:** 8,000 tokens per minute and about 4,000–4,800 tokens per question, so fewer than two questions a minute.
  Rapid questions may be answered by the fallback model or the offline planner (labelled).
- **Guardrail limits:** value-based grounding can't tell a corrupted figure from an equal legitimate one (the 2.3% red-team misses).
- **One data profile per deployment**; Sign in with PayPal identifies the user, but data isn't multi-tenant.
- **Forecasting:** monthly recurrence only, one deterministic path (ranges come from the separate stress test), 90-day horizon.
- **Operations:** no database migration tool (startup adds new columns), in-process rate limit, no hosted public deployment.
- **No LICENSE file yet** (see below).

## Security note

- Never commit `.env` or API credentials. `.env` is gitignored, and the repository and its history contain no keys.
- Use **Sandbox** credentials for demos. Never use live credentials or real payment details with this project.
- Don't post real payment credentials or personal financial data in public issues.
- Every payment step is enforced server-side: acknowledgement before creating an order, PayPal approval, and `confirm: true` to capture.
