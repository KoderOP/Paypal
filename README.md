# FINORA: simulate before you pay

**A PayPal + AI copilot that checks a payment against your future cash flow, then drafts the PayPal checkout. Only you can send it.**

> *"Should I buy a ₹75,000 laptop?"*
> FINORA's Groq agent runs the purchase through a deterministic 90-day model of your PayPal cash flow.
> Paying in full today takes you **below your safety buffer** before payday. Waiting is safe. **PayPal Pay in 4 is safe and
> gets you the laptop today**, so that's the recommendation. Say *"go ahead with Pay in 4"* and the agent drafts the
> PayPal checkout. You review it, approve on PayPal and confirm the capture. The four instalments then appear in your forecast
> (as a simulated schedule: PayPal decides real Pay Later terms at checkout).

**The demo profile is fictional.** About 285 synthetic transactions, generated by FINORA in PayPal's Activity-report format,
none from a real customer or from PayPal. A *Sample data* strip stays on every page while it's loaded, and every transaction
carries a recorded source (see [Data provenance](#data-provenance)).

Most finance apps tell you what you already spent. FINORA works **at the moment of decision**, before the money leaves, and
connects that decision to the PayPal rails (Orders API, Pay Later, Subscriptions, Transaction Search) that act on it.

### PayPal Sandbox setup (verified end to end)

1. developer.paypal.com → Apps & Credentials → **Sandbox** app → copy the client id and secret into `.env`.
2. PayPal Sandbox doesn't accept INR orders (`422 Currency code is not currently supported`), so set
   `PAYPAL_CHECKOUT_CURRENCY=USD` and `PAYPAL_CHECKOUT_FX_RATE=84` (INR per USD, your choice). ₹75,000 is then charged as
   **USD 892.86**, and the twin keeps the ₹ amount. Without a rate, cross-currency checkout is refused, so it never charges $75,000.
3. Approve with a **US-registered** sandbox *Personal* account (Testing Tools → Sandbox Accounts → Create → Country: United States).
   India-registered sandbox buyer accounts are refused by PayPal ("the currency you have chosen can't be taken").
4. `cd backend && python -m evals.check_paypal` makes a real sign-in to PayPal's API, a $1 order and (`--capture ID`) a capture,
   using the app's own client code.

## What makes it different

1. **The model talks, the engine counts, you pay.** The LLM chooses among 7 engine tools and phrases the answer. It never
   computes. A **grounding guardrail** extracts every amount, percentage and date from the draft and checks it against the tool
   results. Ungrounded drafts are replaced with the engine's own wording, and the answer says so.
2. **Agentic, with a human gate built into the architecture.** The agent's only action tool, `prepare_paypal_checkout`,
   returns a proposal card. There is no tool that moves money. Paying needs three human steps: acknowledge (an extra tick if
   the option breaks your buffer) → approve on PayPal → confirm capture. Each step is enforced server-side (`422` without it).
3. **A transparent trace on every answer.** Each model round, tool call (with arguments), token count and guardrail verdict
   is shown under the answer in "How this answer was produced".
4. **Evaluated, not asserted.** Three reproducible evaluations (below), surfaced in-app at `/evals`.
5. **Graceful degradation.** Groq rate limits, malformed tool calls, retired models and outages are retried, swapped to the
   fallback model, or answered by the deterministic planner, and the trace shows which path ran.

## Evidence (`cd backend && python -m evals.run_all`)

### Forecast backtest on synthetic histories

This measures whether the forecast supports the purchase decision. It is **not** a measure of accuracy on real users.

| | |
|---|---|
| **Dataset** | Synthetic only: 30 seeds × 2 personas (salaried; USD freelancer paid via PayPal) = 60 six-month histories, from the same generator family as the demo. A *noise-injected* condition adds late income (−3…+4 days), 10% skipped bills, random one-off expenses and ±25% monthly variable spend. |
| **Method** | Walk-forward: 5 cut-offs per history. Each model sees only transactions before the cut-off and forecasts 30 days of daily balances. *Decision*: is a purchase of 10–150% of monthly income, made on the cut-off day, safe above the ₹20,000 buffer? *False-safe*: predicted safe, actually breached. |
| **Baselines** | Flat balance · linear drift (90-day average daily net flow) · seasonal naive (replay the last 30 days, a strong baseline for monthly cash flow). |
| **Limitations** | The generator has the monthly structure the twin looks for, which favours it; real histories are messier. Single deterministic path, 30-day horizon. Run it on a real export with `python -m evals.forecast_backtest --file <PayPal export.csv>`. |

| Noise-injected condition (300 forecasts per model) | Decision accuracy | False-safe | Daily balance error (% of income) |
|---|---|---|---|
| FINORA twin | **95.0%** | **3.5%** | **15.6%** |
| Seasonal naive | 92.6% | 4.6% | 20.0% |
| Linear drift | 76.6% | 23.4% | 32.3% |
| Flat balance | 77.2% | 22.8% | 35.2% |

On clean synthetic histories the twin reaches 96.8% (seasonal naive 93.2%). Full tables: [docs/EVALUATION.md](docs/EVALUATION.md).

### AI grounding and agent

| Evaluation | Result | Baseline / ablation |
|---|---|---|
| **Guardrail red-team**: 262 seeded corrupted drafts, 154 faithful drafts | **97.7%** caught, **0%** false rejections | Flat 1% tolerance: 76.3% caught (digit swaps: 29.6% vs 100%) |
| **Agent benchmark**: 40 questions, deterministic planner (offline) | Tool 85% · args 77.5% · **grounded 100%** | 100% on wording it was written for, 57% on held-out paraphrases |
| **Agent benchmark: live Groq** (`openai/gpt-oss-120b`), same 40 questions on the fictional profile | Tool **92.5%** · args **90%** · **grounded 100%** · p50 1.7 s | 100% / 100% on planner-known wording, 78.6% / 71.4% on held-out paraphrases (planner: 57.1% / 35.7%). 15% fell back to the planner after provider errors; 17.5% of drafts were rewritten by the guardrail (7.5–20% across three runs) |

The evaluations found and fixed four guardrail bugs, including a JSON-escaping bug that turned "₹12,469" into 912469
and a flat tolerance that let digit transpositions through. Regression tests cover each one.

## Data provenance

Every account records **where its data came from** when it is stored. It is never inferred from file format, and different
sources never share an account:

| Origin | What it is | How it's labelled |
|---|---|---|
| `sample` | FINORA's fictional profile (*Launch the live demo*, or an uploaded `finora-demo-*` / `SAMPLE…`-id file) | Amber *Sample · fictional* badge + the *Sample data* strip on every page |
| `user_import` | A file you uploaded (PayPal Activity export, bank statement, transaction list) | *Your imported file* |
| `paypal_api` | Records returned by PayPal's Transaction Search API, with environment (sandbox / live / demo) | *PayPal Sandbox · Transaction Search* |
| `paypal_checkout` | Payments captured through FINORA's Orders API checkout, with environment | *PayPal Sandbox · Orders API capture* |

- **The PayPal Hub counts only `paypal_api` and `paypal_checkout` as PayPal records.** Sample rows in PayPal's format are
  shown separately as "not from PayPal". It also reports a live credential test, the last Transaction Search outcome, and
  each checkout's state (`awaiting_approval` → `approved` → `captured`, or `failed` / `cancelled`) with PayPal order and
  capture IDs. Agent proposals are *proposed* (not stored); simulations are *simulated*.
- **Reconciliation:** the balance is always Σ opening balances + Σ transactions. Dashboard, agent and simulator share one
  snapshot and one reference date (tested in `tests/test_provenance.py`).
- **Fictional and real data never share a ledger.** Adding real data (a Transaction Search sync or your own file) while the sample
  is loaded is refused (409) unless you replace it, and vice versa. Otherwise one balance would mix fictional and real money.
  Checkout captures are the exception: they are the demo payment itself, recorded in their own labelled account.
- PayPal transaction IDs are stored once per user, so an Activity export plus an API sync of the same account don't double count.
- **Currencies:** Transaction Search records in your home currency are stored as-is. Records in `PAYPAL_CHECKOUT_CURRENCY` are
  converted at your `PAYPAL_CHECKOUT_FX_RATE`, keeping the original amount, fee and rate. Any other currency is skipped and
  reported, never stored at face value. Deposits, withdrawals, transfers and opening funding are stored as transfers, not income.
- Databases created before provenance tracking are migrated at startup, and their old rows are labelled `unknown`, not guessed.

## Architecture in one picture

```
 PayPal Transaction Search / Activity CSV / bank CSV
            │ normalise (PayPal txn id = idempotency key; FX keeps PayPal's own rate + fee)
            ▼
 ┌──────────── deterministic engine (pure, Decimal-only, no I/O, no LLM) ────────────┐
 │ twin.py  recurring detection · variable spend │ forecast.py  90-day daily path      │
 │ payment_options.py  now / wait / Pay Later    │ goals.py  max safe spend, safe date │
 │ scenarios.py  composable what-ifs             │ stress.py  shocks + Monte Carlo     │
 └───────────────────────────────▲────────────────────────────────────────────────────┘
                                 │ 7 tools (JSON schema)
 ┌──────────── agent (app/ai) ───┴────────────────────────────────────────────────────┐
 │ Groq chat completions + tool calling ⇄ tools → guardrail (₹ · % · dates) → reply    │
 │ fallback: deterministic intent planner · trace · token/latency accounting           │
 └───────────────────────────────┬────────────────────────────────────────────────────┘
                                 │ prepare_paypal_checkout = proposal only
                                 ▼
  You: acknowledge → PayPal approve (Orders API, Pay Later) → confirm capture → twin updated
```

## Feature map

- **Ask FINORA** (`/assistant`): the agent. Purchase decisions, affordability ("most I can spend", "earliest safe date"),
  composable what-ifs, stress tests, cross-border income, follow-ups that build on the previous answer, drafted checkouts.
- **What-if Simulator** and **Stress Test**: the same engine through forms and charts. Compare up to four scenarios;
  shock library plus a seeded Monte Carlo of your own spending variability.
- **PayPal Hub**: Transaction Search sync, Activity CSV import, Orders API checkout, Pay Later, Subscriptions API
  (link / cancel / suspend), optional Sign in with PayPal.
- **Cross-border income**: for freelancers paid via PayPal. Fees, PayPal's applied FX rate vs a reference rate, FX and
  late-client sensitivity.
- **Overview / Twin / Transactions**: the model itself, with explicit assumptions.
- **Evaluation** (`/evals`): the committed evaluation results.

## Honest limitations

- **What was verified live, and what wasn't.** Groq tool calling was verified (benchmark above). PayPal Sandbox was verified
  through the app: OAuth (live *Test connection*), Orders v2 create → approval by a US sandbox buyer → capture with
  confirmation → PayPal reports `COMPLETED` (USD 892.86) → twin updated, and **Transaction Search** (a real sandbox record
  synced, converted from USD at the configured rate, stored as `paypal_api / sandbox`). Not verified live: Subscriptions API
  actions, Log in with PayPal, and a Pay Later (Pay in 4) approval. These are covered by mocked-HTTP tests and demo mode only.
- **Pay Later terms are illustrative inputs.** PayPal decides eligibility, APR and schedule at checkout (the buyer chooses on
  PayPal's page). FINORA records instalments from the option you chose, which may differ from what PayPal finally offers.
- **Currency conversion uses your rate**, not PayPal's. FINORA never fetches FX rates.
- **Pay Later after capture is a simulated schedule.** All instalments, including the first, are recorded as upcoming
  obligations from FINORA's illustrative terms. In reality PayPal charges the first instalment at checkout and sets the terms.
- **Sample detection on upload** relies on FINORA's markers (`finora-demo-` filename or `SAMPLE…` ids). A synthetic file from
  elsewhere would be labelled as your imported file.
- **The live Groq benchmark uses the fictional sample profile**, like the other evaluations; none of them measures accuracy on
  real customers.
- **Groq free tier: 8,000 tokens per minute**, about 4,800 tokens per question, so under 2 questions a minute. A long rate
  limit switches to the fallback model, and if that fails too, the deterministic planner answers (the trace shows which ran).
- **Value-based grounding** can't tell a corrupted figure from a coincidentally equal legitimate one (the 2.3% red-team misses).
- **One data profile per deployment.** Sign in with PayPal identifies the user but data isn't multi-tenant yet.
- Forecasts detect monthly recurrence only and produce one deterministic path (bands come from the separate stress test).
- No database migrations (`create_all`). The rate limit is in-process (use a shared store behind a load balancer).

Not financial advice. Projections are estimates from your own history.
